# 01. Концепция и границы

## 1. Цель

Создать полноценный PDM-модуль управления данными об изделии. Модуль хранит компоненты (сборочные единицы и детали) и их документы, ведёт версии, состав и применяемость, организует согласование и подписание и обеспечивает внесение изменений по ЕСКД. Автоматическая проверка чертежей и спецификаций (существующий движок правил) встроена в процесс как контроль качества перед согласованием.

## 2. Что входит и что нет

| Входит | Не входит |
|---|---|
| Компоненты, документы, версии, состав, применяемость | САПР (КОМПАС-3D и другие), моделирование |
| Изменения по ИИ, ПИ, ПР, ДИ | ERP, MES, бухгалтерия (только обмен данными) |
| Согласование, подписание, нормоконтроль | Складской учёт и производство |
| Поиск, отчёты, печатные формы, уведомления | Управление проектами (кроме простых контрольных рубежей, см. 02) |
| Автоматическая проверка документов | Полнотекстовая аналитика по содержимому моделей |

Модуль занимает роль системы управления данными об изделии (АС УДИ по ГОСТ Р 58675): данные, созданные в прикладных системах, размещаются и хранятся в нём, а обмен между прикладными системами идёт через него. Это значит, что модуль обязан контролировать целостность, непротиворечивость и полноту данных (Решение принято, D-01).

## 3. Термины

| Термин | Значение |
|---|---|
| Компонент | Сборочная единица или деталь с обозначением. Хранит версии, документы, связи состава. |
| Документ | Любой документ компонента: основной, сопроводительный, эксплуатационный, технологический. |
| Версия | Неизменяемый снимок документа или компонента после утверждения. Основная: 1.0, 2.0… Временная (по ПИ): 1.1, 1.2… |
| ЭСИ | Электронная структура изделия: состав компонентов и связи между ними. |
| ИИ | Извещение об изменении. Основание для любого изменения подлинников. |
| ПИ | Предварительное (временное) извещение: изменение копий в производстве. |
| ПР | Предложение об изменении. Документацию по ПР менять нельзя. |
| ДИ / ДПИ | Дополнение к ИИ / ПИ: правка граф самого извещения. |
| Держатель подлинников | Организация или подразделение, которому разрешено менять подлинники. |
| Вторичное представление | Файл для просмотра и согласования, получаемый из исходного (PDF чертежа, облегчённая 3D-модель). |
| ХР | Характер работы при подписании: Разработал, Проверил, Согласовал, Начальник отдела, Н. контроль, Т. контроль, Утвердил. |

## 4. Обязательные принципы

1. Изменение это новая версия документа или новый документ. Утверждённую версию исправлять нельзя.
2. Если изменённое изделие взаимозаменяемо с ранее изготовленными, версия новая, обозначение прежнее. Иначе это новый компонент с новым обозначением.
3. Изменение всегда идёт по извещению, где указаны суть, основание и изменяемые версии.
4. Любое изменение меняет состояние и применяемость прежней версии.
5. Подлинники меняет только держатель подлинников. Ошибочное изменение исправляют новым ИИ.
6. ПР не меняет документацию и не порождает версий.
7. Версия родителя не создаётся автоматически при изменении потомка (D-05).
8. Данные об изделии размещаются и хранятся в модуле, прикладные системы работают с ним, а не друг с другом напрямую.

## 5. Роли и права

Обобщённые роли в процессах согласования:

| Роль | Что делает |
|---|---|
| Разработчик | Создаёт и дорабатывает документы и данные, отрабатывает замечания, подписывает с ХР «Разработал». |
| Инициатор процесса | Запускает согласование, следит за ходом. Обычно разработчик или ответственный за комплект. |
| Согласующий | Проверяет, фиксирует замечания, подписывает с назначенным ХР (Проверил, Согласовал, Начальник отдела, Н. контроль, Т. контроль, Утвердил). |
| Подписчик | Наблюдает за ходом процесса, без права подписи. |
| Внешний согласующий | Не пользователь системы, согласует вне системы, фиксируется вручную. |
| Архивариус (БТД) | Регистрирует извещения и документы, проводит изменения. |
| Держатель копий | Выпускает ПР и ПИ. |
| Администратор | Настраивает типы, атрибуты, маршруты, права, правила взаимосвязи. |

Права назначаются по трём измерениям: роль, тип объекта, состояние. Право на смену состояния проверяется отдельно для каждого правила перехода. Минимальный набор прав: просмотр, создание, редактирование в «Проектировании», отправка на согласование, подписание, проведение изменения, администрирование.

## 6. Жизненный цикл (состояния)

Состояние является характеристикой объекта и документа и однозначно определяет стадию его жизненного цикла. Набор состояний по методологии:

| Состояние | Смысл | Ограничение по числу версий |
|---|---|---|
| Проектирование | Версия в разработке | Допустимы несколько версий (варианты), перед согласованием выбирают одну |
| Согласование | Версия на согласовании | Допустимы несколько версий по разным предварительным извещениям |
| Утверждён | Версия успешно согласована | Одновременно не рекомендуется больше одной версии |
| Введено по ПИ | Версия введена временно на срок ПИ | Допустимо несколько, по разным ПИ |
| Архив | Версия зарегистрирована в электронном архиве, действует | Одновременно не рекомендуется больше одной |
| Заменён по ИИ | Заменена новой версией по ИИ | Любое число (история) |
| Аннулирован | Не подлежит использованию, конечное состояние | Любое число |

Названия состояний можно изменить в интерфейсе, но смысл и переходы остаются. Для переходов определяются условия, обязательные подписи и роли с правами (часть 05).

## 7. Применяемость

Применяемость характеристика версии, определяющая условия её применения. Поддерживаются три типа:

| Тип | Назначение | Как присваивается |
|---|---|---|
| Номер | Номера экземпляров изделий, для которых введена версия | При внедрении в производство |
| Период действия | Диапазон дат, когда версия актуальна | Открывается при проведении извещения или утверждении по процессу, закрывается при проведении замены или аннулирования |
| Литера | Литера по ГОСТ | Присваивается при выпуске или по извещению |

Просмотр состава изделия возможен «по дате» с использованием периодов действия.

## 8. Нормативная база

Основные стандарты, на которые опирается ТЗ (актуальный список по состоянию на 2026 год ведётся в методологии на странице «Нормативная база CT3D»):

- ГОСТ Р 2.001-2023, 2.005-2023 (общие положения, термины);
- ГОСТ Р 2.051-2023, 2.052-2024, 2.053-2023, 2.056-2024, 2.057-2024, 2.058-2023 и ГОСТ 2.054-2013, 2.055-2014 (электронные документы, модели, структура, описание изделия, спецификация);
- ГОСТ Р 2.101-2023, 2.102-2023 (виды изделий и комплектность документов);
- ГОСТ Р 2.104-2023, 2.105-2019, 2.106-2019, 2.109-2023 и ГОСТ 2.113-75, 2.124-2014 (основная надпись, текстовые документы, чертежи, групповые документы, покупные изделия);
- ГОСТ Р 2.201-2023 (обозначения);
- ГОСТ Р 2.503-2023, 2.504-2021 (изменения);
- ГОСТ Р 2.525-2024 (электронная структура конструктивная, формат данных);
- ГОСТ Р 2.621-2024 (электронная эксплуатационная документация, формат данных, с 01.03.2025);
- ГОСТ Р 3.102-2024 (стадии разработки технологических документов, с 01.01.2026);
- ГОСТ Р 58675-2019 (АС УДИ);
- 63-ФЗ «Об электронной подписи».

Перед проектированием разделов про состав и эксплуатационную документацию нужно прочитать ГОСТ Р 2.525-2024 и 2.621-2024 как форматы обмена.
