# 06. Данные и интеграции

## 1. Модель данных

Состав первой версии. Названия сущностей рабочие.

| Сущность | Основные поля |
|---|---|
| `Component` | id, обозначение, наименование, тип (сборочная единица или деталь), папка, держатель подлинников |
| `ComponentVersion` | component_id, номер, состояние, период действия (от и до), литера, номера экземпляров, change_id |
| `Document` | component_id, тип из справочника, порядок, обязательность |
| `DocumentVersion` | document_id, номер, состояние, период действия, change_id, replaces_version_id |
| `FileObject` | id, хэш содержимого, размер, формат, дата загрузки, автор |
| `FileRef` | document_version_id, file_id, роль (исходный, вторичное представление, нейтральный формат) |
| `Link` | parent_component_id, child_component_id, тип связи, количество, позиция, раздел |
| `Material`, `Assortment` | справочные записи с атрибутами и ГОСТ |
| `Lock` | объект, владелец, время взятия, срок |
| `Variant` | document_version_id, имя варианта, автор, выбран ли |
| `Change` | вид (ИИ, ПИ, ПР, ДИ, ДПИ), номер, состояние, источник, причина, срок, автор, держатель подлинников |
| `ChangeItem` | change_id, объект, действие (создать версию, аннулировать, сменить статус), прежняя и новая версии |
| `ChangeContent` | change_id, объект или общее, блоки: текст, изображение, комментарий |
| `ImpactDecision` | change_id, затронутый родитель, решение (не затрагивается, пересмотреть, новая версия), обоснование, автор, дата |
| `LinkRule` | исходный тип, действие, обязательный связанный объект, уровень (обязательно, предупреждение, справочно) |
| `DocumentType` | группа, применимость, обязательность, форматы, значок, порядок |
| `Workflow`, `Stage`, `Task` | шаблон, стадии с ХР, задания и их состояния |
| `Signature` | версия, пользователь, ХР, вид подписи, время, контрольная сумма |
| `InfoSheet` | информационно-удостоверяющий лист: обозначение, вид, код, дата, листов |
| `CheckRun`, `Finding` | запуск проверки, версия, замечания (код, текст, уровень), связь с `Change` |
| `Notification` | событие, адресат, канал, статус |
| `Numerator` | префикс, область, текущее значение |
| `Attribute`, `AttributeValue` | определения и значения атрибутов |
| `AuditLog` | кто, когда, что, до и после |
| `User`, `Role`, `Permission` | пользователи, роли, права по типам и состояниям |

Принципы данных:
- версии неизменяемы после утверждения, состояния меняются только по правилам переходов;
- связи состава ссылаются на компонент, не на версию;
- журнал аудита неизменяем;
- все справочники (типы документов, значки, правила взаимосвязи, нумераторы) хранятся в данных и редактируются без кода.

## 2. Интеграции

Принцип: прикладные системы обмениваются через модуль. Прямой обмен между САПР, ERP и MES запрещён, чтобы сохранять целостность данных.

| Система | Что обмениваем | Направление |
|---|---|---|
| КОМПАС-3D | Состав, свойства, основная надпись, чертежи, модели | Модуль ⇄ КОМПАС (часть 03) |
| ERP, 1С | Состав изделия, обозначения, нормы, материалы | Модуль → ERP, сверка в обе стороны |
| MES | Технология, маршруты, нормы | Модуль → MES |
| Почта | Уведомления | Модуль → почта |
| Каталог пользователей (AD, LDAP) | Учётные записи, подразделения, группы | Каталог → модуль |
| ЛОЦМАН:PLM | Импорт и экспорт, если потребуется параллельная эксплуатация | Двусторонний, по необходимости |

Для обмена вводится слой унификации: общие термины, типы данных, единицы измерения, обнаружение конфликтов обмена и обновления, возможность их разбора и исправления. Модели обмена настраиваются, а не пишутся кодом.

| № | Требование |
|---|---|
| INT-01 | Единый слой интеграции: сопоставление терминов, типов и единиц измерения. |
| INT-02 | Обнаружение и разбор конфликтов обмена, журнал обмена. |
| INT-03 | Настройка моделей обмена без изменения кода. |
| INT-04 | Интеграция с каталогом пользователей. |
| INT-05 | Выгрузка состава и атрибутов в ERP, формат согласуется. |
| INT-06 | Открытый API модуля для внешних систем с правами и журналом. |

## 3. Миграция

В методологии отдельного описания миграции нет. Единственный близкий подход: проект ввода применяемости, когда ранее утверждённым документам назначают применяемость в рамках проекта ввода системы. Для нас предлагается следующий порядок.

1. Инвентаризация: список существующих документов (PDF чертежей, 3D с сервера, спецификации, МК, ТП, эксплуатационные).
2. Сопоставление: определение компонента по обозначению, привязка документов к компонентам по правилам именования.
3. Присвоение начальных версий 1.0 и состояний (по умолчанию «Архив», действующая). Период действия открывается датой миграции или фактической датой утверждения, если она известна.
4. Построение состава из спецификаций и сверка с Excel.
5. Отчёт о несопоставленных и неоднозначных документах, разбор вручную.
6. Параллельная эксплуатация, пока тестеры работают на старой версии (обратная совместимость по `docs/MIGRATION.md`).

| № | Требование |
|---|---|
| MIG-01 | Пакетная загрузка существующих документов с сопоставлением по обозначению. |
| MIG-02 | Начальные версии и состояния, периоды действия, назначение применяемости. |
| MIG-03 | Построение состава из спецификаций и сверка с внешним источником. |
| MIG-04 | Отчёт о несопоставленных и конфликтных документах. |
| MIG-05 | Сохранение кодов и текстов замечаний прежней версии (обратная совместимость). |
